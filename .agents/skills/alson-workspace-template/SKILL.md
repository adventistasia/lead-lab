# Alson Workspace Template
**AI-generated by:** Alson (A.I Agent)

This skill creates or configures reusable workspaces from the bundled Alson workspace skeleton. It preserves the separation between routing, stable references, and run-specific artifacts, and adds a quality-gated correction loop with resumable runs.

## Scope

Use this skill for:

- Creating a new workspace from the bundled skeleton
- Configuring an existing workspace that follows the skeleton
- Defining or revising workspace routing
- Creating a stage from the stage contract template
- Adding or configuring the final Measure and Learn stages
- Checking a workspace against the validation checklist
- Explaining how the workspace architecture should be applied during setup

Do not use this skill for:

- Running a configured workspace stage
- Producing a project or business artifact
- General project-management advice
- Building or installing an agent skill package

## Workflow

### 1. Identify the task

Route the request to the smallest useful operation:

| User intent | Load | Result |
|---|---|---|
| Create or initialize a workspace | `templates/workspace/setup/CONTEXT.md`, `questionnaire.md`, and `validation-checklist.md` | Configured workspace plan or workspace files |
| Configure workspace-wide behavior | `templates/workspace/AGENTS.md`, `CONTEXT.md`, and `_config/` | Updated identity, routing, or stable configuration |
| Define a stage | `templates/workspace/stages/_TEMPLATE/` | One concrete stage contract and folders |
| Validate a workspace | `templates/workspace/setup/validation-checklist.md` and the files under review | Pass or fail findings |
| Explain the architecture | `templates/workspace/README.md` and the minimum relevant template file | Plain-English explanation |

If the request combines operations, run only the required operations in order.

### 2. Confirm before writing

Before the first write:

1. Identify the destination workspace.
2. Confirm the intended outcome.
3. Check whether the destination already contains files.
4. State what will be created or changed.
5. Get confirmation when the destination or scope is not already explicit.

Never overwrite an existing workspace or source file without explicit permission. Do not invent a destination, source location, owner, approval, or stage requirement.

### 3. Set up the workspace

For a new workspace:

1. Use the bundled skeleton as the starting structure.
2. Read the setup contract and ask only the questions needed to configure the workspace.
3. Collect setup answers in plain English. Ask one question at a time when clarification is needed.
4. Define the workspace outcome, users, routes, inputs, references, outputs, review gates, and verification checks.
5. Configure the quality threshold, acceptance criteria, rubric, correction routes, and human-only interventions.
6. Replace placeholders in the copied workspace files. Preserve the template's folder roles.
7. Create only the production stages needed for the stated outcome, then keep the quality-gate and next-action roles as the final two stages. Measure and Learn are the default names.
8. Record setup decisions in `setup/initialization-record.md` in the configured workspace.
9. Run the validation checklist before any work stage runs.

Stop when a required answer, review, input, or validation check is missing.

### 4. Define stages

Every executable stage must have one explicit interface:

```text
Declared Inputs -> One Transformation -> Declared Outputs
```

For each stage:

- Name the exact files or locations it may read.
- State the one transformation it owns.
- Name every output, path, format, and intended consumer.
- State the input gate and stop conditions.
- Define verification checks before the output is passed downstream.
- Add a review or approval gate when human judgment affects later work.
- Declare the Measure correction input when the stage can repair a quality finding.
- Declare `run-state.md` when the stage can block, pause, or resume work.

Use a stage name with a numeric prefix for sequential work, or a capability name for independently invoked work. Do not add hidden state or undeclared side effects.

### 5. Validate

Run `templates/workspace/setup/validation-checklist.md` against the configured workspace. Check structure, stage interfaces, context discipline, flow, user experience, and traceability.

Report each failed check with the file or stage that needs correction. Do not pass known-invalid work to a downstream stage. If a recurring defect is found, recommend changing the source instruction, reference, or routing rule instead of repeatedly editing outputs.

## Operating Rules

- Read only the files needed for the selected operation.
- Keep `AGENTS.md` focused on workspace-wide behavior.
- Keep `CONTEXT.md` focused on routing and context loading.
- Keep stable rules in `_config/`, `references/`, or `shared/`.
- Keep run-specific inputs and outputs in the relevant stage folders.
- Make stage dependencies explicit and one-way.
- Prefer existing sources over duplicated copies.
- Do not copy external source material unless the workflow requires it.
- Stop on missing or invalid required inputs.
- Stop at review and approval gates.
- Route a failed final quality gate back to the responsible production stage and measure again.
- Write `Blocked` or `Paused` state before stopping and resume from that state when requested.
- Re-run only the affected stage when an input or rule changes.
- Keep generated artifacts inspectable and editable.
